# Product

## Register

product

## Users

JARVIS is built first for Prince Anozie as a personal AI operating environment. The user is usually inside an active work session: asking for help, reviewing governed actions, inspecting memory or project context, validating model/provider behavior, or checking whether an automation path is safe to open.

Secondary audiences include future maintainers, reviewers, and portfolio observers who need to understand that JARVIS is a governed local-first system, not a generic chatbot wrapper.

## Product Purpose

JARVIS exists to become a trusted command center for local-first AI work. Its purpose is to coordinate models, tools, memory, voice, approvals, telemetry, knowledge systems, and future service adapters through explicit governance boundaries.

Success looks like a user being able to see what JARVIS knows, what it is doing, what it is not allowed to do, and what requires approval without hunting through logs or trusting hidden autonomy.

## Brand Personality

Precise, cinematic, and governed.

The interface should feel like an operational control room for a capable AI system: calm under pressure, explicit about authority, visually distinctive, and serious about evidence. It should have atmosphere, but never at the cost of scannability or safety.

## Anti-references

JARVIS should not look like:

- A generic SaaS dashboard with interchangeable gray cards.
- A chatbot wrapper with a decorative AI skin.
- A purple-blue gradient startup landing page.
- A marketing hero pretending to be an application.
- A toy assistant that hides uncertainty, authority, or caveats.
- A dense admin panel that buries status and approval state in undifferentiated boxes.

## Design Principles

1. Governance is visible. Authority state, consent, disabled paths, confidence, and caveats must be readable at the surface level.
2. The orb is the system presence. It should act as the emotional and operational signal for mode, load, posture, and attention.
3. Density serves command. The UI can be information-rich, but it must be organized into clear rails, panes, queues, and evidence surfaces.
4. Metadata over spectacle. Visual drama is earned by state, not decoration. Raw prompts, secrets, source bodies, and private payloads stay out of UI chrome and telemetry.
5. Local-first is a design posture. Cloud, automation, writes, and elevated authority should always feel opt-in, gated, and auditable.

## Accessibility & Inclusion

Target WCAG AA as the practical baseline for future UI work. Critical states cannot rely on color alone; use labels, icons, copy, and structure. Dense operational surfaces need visible keyboard focus, reduced-motion support, readable small text, and enough contrast for muted metadata. Motion should communicate status changes and must respect `prefers-reduced-motion`.
